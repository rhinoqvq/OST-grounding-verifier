# 附录：逐版本数据（OP0 → OP29）

[返回版本迭代](../version-history.zh-CN.md) · 数据文件：[`data/versions_qa900.csv`](data/versions_qa900.csv)

正文[版本迭代](../version-history.zh-CN.md)只讲关键节点，这里是每个版本的数字和改动的来龙去脉。数字都来自当时的结果文件和调用台账，按同一口径重算，没有新跑模型。

## 读表须知

- **开发集**：RAGTruth 的 900 条 QA 回答（QA-900）、20 题小手写集 cases20、各套探针。这些在开发中反复用来找错、做验收，分数只能说明在见过的数据上的表现，不能当泛化证据。
- **外部基准**：LLM-AggreFact 官方完整测试集，跑前写了预登记。

**指标：**

| 指标 | 意思 |
|---|---|
| 响应级 F1 | 一条回答里有没有幻觉，只要报警一处就算这条报警。RAGTruth 排行榜的口径。召回一直在 97–99%，变化基本都在精度上 |
| 严格整题 | 900 条里，金标标出的每个幻觉都报出、而且一处都没多报，才算这条对 |
| 字符级 F1 | 报警范围和金标幻觉片段逐字符比对，RAGTruth 论文的口径，量的是「标得准不准」 |
| span 命中 | 235 个金标幻觉片段里，被报警范围碰到的有几个（有一点重叠就算）。只是代理指标，报得越宽越占便宜 |

**噪声**：同一份代码重跑两次，响应级 F1 差 0.1–0.2，严格整题差 1–2 条。表里小于这个幅度的变化不算变化。

**噪声**：同一份代码重跑两次，回答级 F1 差 0.1–0.2，严格整题差 1–2 条。表里小于这个幅度的变化不算变化。

## 各版本在迭代什么

这里按更细的六段讲。阶段一就是正文的「换拆分方式」；阶段二到五合起来是「语义树与算子开发及调整」；阶段六是「模块及组合的消融实验驱动的推理管线优化」。

每一版都是先测到一个具体的失败，再改，改完对照跑之前定好的验收线。下面的「结果」和前面几张表用同一套口径。

### 阶段一　换拆分方式：OP0 → OP1

**OP0（0fd6d04）初版：生成式模型拆分回答，Jev 判定**
- 起因：第一次接真实 API，作业样例里 NFS 那条，Jev 判 C 的把握是 1.0，但证据的相关性打分是 0.59，差 0.01 没过 0.60 的线，判定被丢掉。同一道题还把只是话题相关的句子挂成了引用。
- 改动：相关性问法加一句「只是话题相同不算证据」；拆分的温度设成 0；判定很确定、但没有句子过线时，取排名第一且分数高于 0.30 的句子当引用。
- 结果：作业样例四条全对。拆分占了 97% 的延迟，中位数约 15 秒。

**OP1（ae32bbd）纯 Jev 拆分**
- 起因：生成式模型拆分太慢，还会顺手改写回答，比如把代词绑到错的主语上、产生碎片和重复。
- 改动：代码在连接词处找切点，Jev 只回答每个切点属于哪一类（两件事、因果、转折、先后、整句保留、不是边界）。切出来的片段都是回答的原文。
- 结果：延迟中位数 15.2 秒 → 0.61 秒，少用一个模型。QA-900 响应级 F1 +0.5，严格整题 252 → 279。遗留问题：名词并列（「V1 and protocol V2」）拆不开。

### 阶段二　补证据和关系：OP2 → OP8

**OP2（4070a71）诊断切分 + 整句出处门**
- 起因：保留整句不切的单元（if、or、转述）里，有依据的大半句会把编造的一小块一起带过去。RAGTruth 上当时漏报的 13 个片段，全是这个形状。
- 改动：这类单元的判定仍按整句，但代码把它切成几块「诊断部件」，逐块问「原文里有没有这块内容」（只查出处，不查真假）。有一块没出处，就把 S 降成 U。
- 结果：补上了这类漏报。代价是 QA-900 F1 −1.3（误报 +28）：干净回答里的转述细节找不到逐字依据，也被降了，而人工标注不算它幻觉。

**OP3（08efdbd）混合证据选择**
- 起因：三套测试集里最常见的失败是引用缺腿。比如「Acorn 项目用 bronze 策略」这种连接前提，单看不像证据，逐句的相关性打分只有 0.3–0.5，过不了线。
- 改动：用嵌入向量做先验，嵌入排名前 2、且相关性分数不低于 0.25 的句子并入证据。嵌入只参与选证据，不参与判定，因为它看不懂否定和数字。
- 结果：小集上 5 处引用缺腿全部补上。延迟中位数 0.63 → 1.83 秒。

**OP4（904e719）嵌入的触发条件**（只跑过小集）
- 起因：OP3 每个请求都调嵌入，RAGTruth 上触发了 3,565 次，真正需要补证据的只有三百多次，其余都是噪声来源，还拖慢延迟。
- 改动：只在多段原文或原文较长时预先触发（和判定同时发出，不增加延迟），或者在判定后证据太薄时补一次。
- 结果：关键引用全部保留，cases20 的延迟 547 → 363 ms。

**OP5（ed19c0e）共享开头的并列切分**（只跑过小集）
- 起因：「accepts protocol V1 and protocol V2」这种共用开头的并列拆不开，只能整块判定。
- 改动：and 的切分题多给几个选项，把补全了开头的第二条 claim 写出来让 Jev 选。拼出来的句子还要过一道检查：两条合起来是不是等于原句，不是就撤销切分。or 不给这个选项，因为拆开析取等于分别断言两边。
- 结果：cases20 能正确拆成两条。

**OP6（0143313）判定题的上下文收窄**（只跑过小集）
- 起因：片段判定时带着整句当上下文，句子里另一半被否定的内容，会把逐字有依据的片段也拖下去。消融实验里，这类片段的判定从 1.00 掉到 0.55。
- 改动：事实片段的判定题加一句说明：上下文只用来理解代词和共享主语，结论只针对这一条。关系单元不加，因为它判的本来就是句子结构。

**OP7（6f167dc）关系分步核对**（只跑过小集）
- 起因：「A 因为 B」用一道题同时找连接、对两边，太难了。合理的实例化被判成 C，范围收窄被判成 U。
- 改动：拆成单步问题，由代码组合。先找原文里是哪句话自己说了这种连接，再分别比两边是相同、相反还是不同的东西。有一边不同 → U；有一边相反 → C；都相同 → S。转折（but）不走这条，直接按成员汇总。句首的「Because A, B」也开始能切了。
- 结果：关系探针 8/10 → 9/10。

**OP8（e20b61e）两跳桥接**
- 起因：「生产环境接受 V2」要从「生产流量全部走 Azure」和「Azure 接受 V2」两句推出来，一道判定题给不出确定的答案（概率约 0.47）。
- 改动：普通判定拿不准时，拆成几个单跳问题：哪句话把主语连到了另一个实体、哪句话说了这个属性、这个连接是不是完整的、属性对不对得上。都成立 → S，并引用两句；属性相反 → C。
- 结果：cases20 第一次整题全对。OP4–8 合起来，QA-900 F1 −1.2（误报 +23），主要来自关系分步核对：原文只是并列写了 A 和 B、没说因果，就判 U。

### 阶段三　补可靠性漏洞：OP10 → OP15

**OP10（06f1ef4，含 61ba538）补三个可靠性漏洞**
- 起因：逻辑探针测出三个洞。太短的片段被直接丢掉，里面的词没人核；先后关系写反了也能判 S，因为两边比对不管方向；桥接时属性说的是第三个实体，也能传过来。另外上一版的措辞，让 RAGTruth 上大量普通的 and 被当成先后关系（152 → 304 个）。
- 改动：太短的片段撤销切分、并回相邻片段；先后关系加一道问方向的题；桥接加一道「属性说的是不是被桥接的那个实体」；措辞改回「普通 and 是两件事」。
- 结果：QA-900 F1 +0.6，收回了 OP8 的过度切分。逻辑探针 14 → 15/17。

**OP11（68d4e61）三个见证算子**
- 起因：判成 C 的输出最不可靠，随机抽样里只有约 25% 是对的。出处门会把原文里逐字就有的 if/when 内容误降成 U。关系里一个拿不准的成员，会把整条关系拖下去。
- 改动：①出处门：部件的文字在原文里逐字出现，就直接算有出处。②关系成员：分步核对已经证明原文说了两边，拿不准的成员不再拖累整条关系。③C 的准入审查：被引的那句话必须明确排除这条 claim，否则降成 U。三个改动都是单向的：要么往 U 压，要么只在有可引前提时升级。
- 结果：QA-900 上判 C 的单元从 284 降到 117。判 S 的输出抽样仍然 97% 正确。

**OP12（61152e3）条件辖域守卫**
- 起因：句首的 if 被判「整句保留」，句中的 because 却被单独切开，结果「内存耗尽」这种条件句里的内容，被当成无条件的事实判成 S。
- 改动：句子里的条件词只要被判整句保留，这句里其他的切分全部撤销。被撤销的位置改成诊断部件，照样查出处。

**OP13（4bb57aa）断言门 + 逐句见证**
- 起因：第二次自查找到三个问题。原文只在 if 条件或转述里提到的连接，也能组合出 S；逐字见证把整段原文归一化以后，跨句号拼出了原文没有的内容（「restarts. Daily」变成「restarts daily」）；倒装条件（「Should the watchdog fire, ...」）识别不出来。
- 改动：关系核对加一问：这句话是不是用自己的口吻断言了这个连接。见证只在单句内匹配。条件词表加上 should、had、were。

**OP14（ab02768）第二轮外部审计修复**
- 起因：外部审计在源码里确认了四个问题。救援升成 S 之后没有再过出处门；见证把符号全删了，+5 和 −5、≤10 和 ≥10 被当成一样；「条件规则 + 另一句确认条件成立」这种推理被错误拒绝；关系的引用漏掉了别处说的别名前提。
- 改动：救援之后重新过出处门；见证保留数字前的正负号、比较符和小数点；新增「另一句确认条件成立」的推理路径；把别名前提加进引用。
- 结果：QA-900 F1 +0.5（误报 −6），压在噪声边上。

**OP15（98449ae）整合**
- 起因：冗余审查发现，好几份连接词表是手工分别维护的，出现过两次不一致；切分投票实测没有用。
- 改动：所有连接词表合成一张角色表；两处「排除」的定义合成一个；删掉切分投票（同一道切分题问 3 次取平均）。
- 结果：前后行为快照一致（只有一处事先声明的改动），QA-900 在噪声内。

### 阶段四　减少误报、堵假 S：OP18 → OP20

**OP18（1ee4bc7）元话语门**
- 起因：「Based on the passages…」「Hope this helps」这类不是事实的句子，被当成 claim 判 U，是 RAGTruth 上误报最多的一类。
- 改动：每个回答句先问一道「这是不是需要核对的事实」，有 0.80 的把握才排除。第一版措辞把「根据原文，费用是 X」这种带框架的事实句也排除了，吃掉了约 11 个真幻觉片段，收窄措辞以后才上线。
- 结果：QA-900 F1 +0.3（误报 −6），span 命中守住了红线。
- 同一轮还试了「拿不准的 U 交给生成式模型二审」（OP17）：严格整题多了约 10 个百分点，但放过了 6 个真幻觉，span 命中跌破红线，没有上线。

**OP19（281f478）减法 R5 + R6**
- 起因：减法审查列出了一批能证明不改变结果的简化。
- 改动：转折关系的结论直接由成员推出，不再先写一个占位的 S 再覆盖；三种救援（桥接、成员、二审）共用同一个升级入口，升级后统一重新过出处门。
- 结果：44 道探针的判定完全一致，QA-900 在噪声内。

**OP20（dfa057e）补 only-if 漏洞**
- 起因：外部的蕴含审查找到两条能走通的假 S：原文写「L only if F」加上「F」，判定器就把 L 判成成立。
- 改动：只改三处措辞，说明必要条件成立不代表结果发生。早期的草稿多改了一处，把几个历史上一直稳定的真 C 也降了，二分定位后去掉。
- 结果：两道 only-if 探针 S → U，70 道历史探针里 68 道判定逐字节相同。

### 阶段五　管线 bug 和两棵树：OP21 → OP26

**OP21（4d4344f）可追溯性**
- 起因：数据审计全部干净，但有两个缺口：模型调用记录没法对应到具体哪一次运行；判定模型用的是「最新版」别名，没有人盯着版本是否漂移。
- 改动：每次模型调用记下运行 id；判定模型固定在 jev-1.13.0，并检查返回的版本号。判定行为不变。

**OP22（43acc52）段落编号从 1 起**
- 起因：失败案例分析发现，回答写「第 3 段」，判定器看到的段落却是从 0 开始编号的，正确的引用被判成没依据，错一位的反而判对。QA-900 被误报的 507 篇干净回答里，有 144 篇是这个原因。
- 改动：给判定器看的段落标签从 1 开始；API 返回的 index 仍然从 0 开始。
- 结果：QA-900 F1 +0.8（误报 −26），严格整题 268 → 292，字符级 F1 22.6 → 26.4。代价是 8 个真幻觉从此被放过，span 命中跌破 0.935 的红线（0.898）。权衡后接受，记为下一个目标：判定器偏宽松。

**OP23（8595b7b）分句修复**
- 起因：列表形式的回答被切错了位置。左括号留在上一句，「(Passage 1)」被切到下一条里；空行和行首的列表符号不算句子边界，相邻的条目被并成一句。
- 改动：括号不再被切开；空行和行首的列表符号一律开始新的一句。原文和回答用同一套规则。
- 结果：字符级 F1 26.4 → 27.8。代价是以冒号结尾的引导句单独成句以后，314 个里有 111 个被判 U，严格整题 292 → 275，跌破事先定的线。权衡后接受。

**OP25（c064d2b）两棵树**
- 起因：最初的设计就是两棵树之间的蕴含：回答拆成树，原文也拆成树，再把回答的节点对到原文的节点上。之前只实现了回答这一侧。
- 改动：每段原文走和回答完全一样的拆分流程。回答里的事实能对上原文的某个片段或句子，就判 S，并引用那个片段；对不上的仍交给整篇原文判定，C 和 U 也只在这一步判。同一个提交还修了长文档：原文太长时，选句子的题只列重叠最多的 60 句；Jev 的请求按 token 预算拆分。这两个上限（255 个选项、约 3.2 万 token）是 AggreFact 全量跑出来的。
- 结果：严格整题 275 → 285。成本 +10%，延迟中位数 0.85 → 1.33 秒。

**OP26（7ba6ecc）原文侧措辞**
- 起因：原文树直接复用回答侧的题目，Jev 被告知每段原文是「正在拆分的回答」。
- 改动：原文侧的题目改成「原文句子」的说法，回答侧逐字节不变。
- 结果：分数不变（4 个单元的判定变了）。这是正确性修复，不是提分。

### 阶段六　消融驱动的管线优化：OP27 → OP29

正文[版本迭代](../version-history.zh-CN.md)和[消融实验](../ablation.zh-CN.md)讲得更细，这里只列每个版本。

**OP27（418ba46）整句护栏**
- 起因：OST 的误报多，而整句判一次的单调用在「这句有没有错」上更准。
- 改动：整句单调用判 S 的句子，撤回 OST 在它上面的片段报警。预登记的四条判据全部通过；窄版和「只放行弱报警」两种变体没过判据，不采用。同一版本还修了 low_confidence 标记误匹配、长原文超 max_tokens、分句「句号 + 脚注编号」边界。
- 结果：QA-900 回答级 F1 39.4 → 47.0，字符级 28.1 → 35.5。

**OP28（ade1fdf）短答案和非拉丁文字**
- 改动：修短答案被误排除；「是不是陈述」那道题支持非拉丁文字。
- 结果：RAGTruth 上判定和 OP27 相同。

**OP29（c78c508）先按句判定**
- 起因：消融显示原文树映射测不出贡献，答案拆分的价值在定位不在检出，还能提升的方向是多撤回误报。
- 改动：整句判 S 的句子直接继承 S，不再做片段判定；护栏扩到整句 U / C、关父节点复核；引文选择题；原文树按长度自动；修了缓存在并发下的问题。
- 结果：RAGTruth 全量回答级 / 字符级 F1 对 OP27 +0.71 / +0.76，成本 $6.91 → $2.57。QA-900 每千条 $1.63 → $0.66。
