# 设计与实现

[返回 README](../README.zh-CN.md)

## 设计思路

在方法 2（基础 llm + harness）的基础上，开始构思优化版本的架构。这一类服务作为幻觉检测，应该在算法的基础上有一定的结构，可以证明结果。在发现服务出错时，核心环节的输入输出应该是可以追踪，且可以说明理由的。

在这个构想的基础上，想到了一种数据结构：语义树。通过算子将服务接受的字符串进行运算，拆分成一棵语义树。然后证明原文中的事实跟 generated answer 直接有蕴含关系，则可判断为 S（SUPPORTED）。如原文明确说了与之相反的内容，则为 C（CONTRADICTED）。最后难以证明蕴含或矛盾的情况则为 U（UNSUPPORTED）。

当时的假设是：把回答拆到最小的语义单位，每一块单独去对原文，模型每次要看的东西更少、更具体，判断会比一次看整段回答更准。而且每个结论都能落到回答里的某一段上，出错时能追到是哪一块出的问题。这个假设后来在第三阶段用消融实验检验过：拆分对标出错在哪确实有用，但拆得越细噪声越多，判断「有没有错」反而变差，拆到什么程度最合适，最后定下来的就是 OP29 的做法，见[版本迭代](version-history.zh-CN.md)。

在拆分语义树部分，通过数理逻辑中的算子来实现，具体来说有这些算子（合取、关系、整句保留、组装、回退，见下面的「算子」）。这些算子使这套算法满足了忠实和覆盖的需求。在这基础上，拆分过头的情况需要有个部分可以兜底，所以在这里抽象出来一个新函数，允许语义树在被拆分过细的情况，如证明到确实是拆分过细了，可以从叶子节点回推到父节点。后来的消融实验显示，这一步关掉更好，OP29 默认关闭，换成了先按整句判定（见下面的「一次判定的流程」）。

这个数据结构是和这个项目高度耦合的。通过这样的数据结构构造的算法，可以满足在可追踪、一定程度防止模型幻觉的前提下，完成证明。

但运用这个算法在这个项目中还有个条件，这个算法的复杂度是远比循环调用 llm 来实现这个服务来的高的。OP29 在开发集 RAGTruth 上，平均每条回答要发约 5 次请求，每次请求最多打包 48 道题。但想让语句进一步的切分到最小语义，又需要 llm 来进行判断。这个时候想到了 jev。不同于生成式大模型，jev 虽然本身也是在 llm 的范畴中，但 jev 的输出是输入进去的回答问题的选项的概率。jev 的好处是极低的模型调用费用和极低的延迟：输入每百万 token $0.042，输出不收费。jev 是非常适合上述算法的实现的。

## 核心算法设计

这个部分讲的是系统架构中，核心算法语义树及算子的部分。

在本项目中的核心算法由可操作的语义树和算子实现函数构成。树本身是内存里的数据结构（[`rag/tree.py`](../src/verifier/rag/tree.py)），每次运行的节点、边、判定和每一次模型调用都记进 SQLite（[`rag/store.py`](../src/verifier/rag/store.py)），所以每个结论都能追溯，也能离线回放。

### 语义树

下面的动图是附带测评集第 15 题第 2 句的一次真实运行：代码提出切点，Jev 判断怎么切，切出来的两条 claim 挂在整句下面，各自判定以后再往上汇总。每一步的概率都来自调用记录，完整输出在 [`appendix/data/sample_ost30_15_op29.json`](appendix/data/sample_ost30_15_op29.json)。

![语义树：一句话怎么拆、怎么建树、怎么判](figures/semantic_tree.zh-CN.svg)

- 原文段落和回答都以不可变的方式存下来（[`rag/source.py`](../src/verifier/rag/source.py)）。树上的每个节点都指向回答里的字符偏移，不存改写过的文字。
- 节点有这几类：
  - **事实**：一条可以单独核对的断言。
  - **关系**：两个成员之间的因果、先后、转折、条件。
  - **整句保留**：条件句、选言句、转述和情态（「可能」「据说」），这些句子里的各部分本身并没有被断言，所以不拆。
  - **句子**：原句本身，是树的根这一层，也是拆不动时的回退单元。
- 判定在树上汇总：严重程度 S < U < C，取最严重的那个（[`judge/aggregate.py`](../src/verifier/methods/optimized/judge/aggregate.py)）。

### 算子

拆分由代码在连接词处提出候选切点，再问 Jev 这个切点属于哪一类（[`semantics/propose_jev.py`](../src/verifier/methods/optimized/semantics/propose_jev.py)）。Jev 只做分类，不写字，所以切出来的片段都是回答的原文。

| 连接词 | 算子 | 为什么 |
|---|---|---|
| and、逗号并列 | 合取：切开，两边分别核对 | 两边都被断言了，任何一边错，整句就错 |
| because、then | 关系：切开，另加一个关系节点 | 关系本身也是断言，要单独核对原文有没有这么说 |
| but | 切开，关系按「and」处理 | 转折不额外断言什么机制，只看两边 |
| if、unless、or、may、转述 | 整句保留 | 切开会把原句没断言的内容当成断言；保留整句，只把关键部件拿去查出处 |
| 共享开头的并列 | 组装：把共享的主语拼回去，让每条都是完整的句子 | 拼完再问一次「合起来意思变没变」 |
| — | 回退：撤销切分 | 切点落在条件辖域里、片段太短、或者拼回检查不过，就撤回 |

这些算子能证明什么、前提是什么，见[附录：语义树的数学论证](appendix/semantic-tree-proofs.zh-CN.md)；哪些逻辑函数是重复的、哪些是必要的，见[附录：逻辑函数的职责重合审查](appendix/redundancy-audit.zh-CN.md)。这些算子要保证两件事：
- **忠实**：切出来的每一块都是原句真正说了的内容。普通切分是回答原文的片段，靠构造保证；组装出来的 claim 是重新拼出来的文字，靠拼回检查来守。
- **覆盖**：所有块合起来不比原句少说什么。这一条只能靠拼回检查和整句判定来守，是概率性的，不是证明。

### Jev 怎么用

Jev（TypeSafe 的 System One）在这个系统里只做选择题，从不写字（[`models/jev.py`](../src/verifier/models/jev.py)）。每次调用发两样东西：一段材料（state），和一批互相独立的题。

- 题有两种。选择题每个选项附一句话说明它是什么意思；是非题只问「是不是」。Jev 对每道题返回概率。
- 拆不拆、判 S / C / U、引用哪句原文，都由代码根据这些概率和阈值来定。Jev 的回答里没有自由文本，所以不存在「模型编了一段话」的情况，也没有解析失败。
- 材料决定 Jev 能看到什么：拆回答时只给回答，不给原文，这样拆分不会被原文带偏；判定时才给原文。
- 题号由代码起，比如 `v::u3`、`cut::A.S1::42`，代码靠题号把答案对回到具体的单元。每个阶段问哪些题，见[附录：Jev 题目清单](appendix/jev-questions.zh-CN.md)。

主要阈值：

| 用途 | 阈值 |
|---|---|
| 切点题，概率到这个数才切 | 0.60 |
| 元话语门，把握到这个数才把一句排除出核对 | 0.80 |
| 判定首选项低于这个数，记 U（倾向 S 的除外） | 0.55 |
| 一句原文算相关证据 | 0.60 |
| 没有一句过相关门槛时，排名第一的那句至少要到这个数才保留作证据 | 0.30 |
| 整句保留单元的关键部件算有出处 | 0.50 |

工程上的处理（[`harness/`](../src/verifier/harness/)）：
- **分批**：同一份材料的题，每次请求最多 48 道，按约 2.8 万 token 的预算切开，同时最多 4 个请求。
- **收窄**：Jev 一次请求大约放 3.2 万 token，原文从不整篇硬塞进一个请求。原文超过 2.6 万 token 时，原文树按段落分窗口建，映射只看对应段落；要对整份原文下结论的判定放不下时，只放和待判内容最相关的句子（先按句判定那一步最多 254 句）。入口上限（单段和总长各 50 万字符）是为了控制成本和延迟。
- **重试**：上游可以重试的错误最多试 3 次，指数退避。
- **固定版本**：固定用 `jev-1.13.0`，每次响应都核对实际服务的版本。
- **录制与回放**：每次调用连同请求、响应、token 用量都存进 SQLite，键是请求内容的哈希。开发集可以离线回放复现，同一个请求不重复计费。

## 一次判定的流程（OP29）

代码在 [`methods/optimized/pipeline.py`](../src/verifier/methods/optimized/pipeline.py)。延迟由轮数决定，不由题数决定，同一轮的题并发发出。

下面的动图是作业里 SQLite WAL 例子的一次真实运行，每一步 Jev 给的概率都是当时记下来的，完整的输出在 [`appendix/data/sample_wal_op29.json`](appendix/data/sample_wal_op29.json)。第二句里有「when」，切点判成整句保留，所以整句没拆开，在先按句判定这一步就直接定为 S。

![一次判定的流程](figures/how_it_works.zh-CN.svg)

1. **准备（代码）**：检查入口上限，存下原文和回答，分句。回答为空就直接返回空列表。原文超过约 2.6 万 token 时，开始在后台建原文树，和下一步并行。
2. **拆回答（Jev，只看回答）**：每个候选切点一道题，每句一道元话语题（「Based on the passages…」这类不是事实的话不进核对），共享开头拆开后再问一道拼回题。所有句子都拆。
3. **先按句判定（Jev，看原文）**：回答的每一句问一次，对照整份原文，判 S、C 还是 U，并选出一句证据。最高选项是 S 而且找到了证据句，这句里的所有 claim 就都定为 S。再给每条 claim 问一道引文选择题，从这句证据和词面最接近的两句里挑出真正说了它的那句，过不了 0.50 就沿用整句的证据。
4. **逐条判定其余的 claim（Jev，看原文）**：
   - 建了原文树的，先把 claim 映射到原文树的节点上，映射不上的再交给整份原文判定。
   - 对整份原文判定：判 S / C / U，同时问每句原文是不是证据。没有一句过相关门槛时，保留排名第一的那句作证据（证据排名回退，消融里证明比「没证据就判 U」更好）。
   - 整句保留的单元，关键部件要过出处门。关系单元分步核对：先找原文里说了这个关系的那句，再核两边和方向。
   - 判 C 之前确认原文的对立是明确的（反驳过滤）。需要两段原文才能支持的 claim，拆成两道单跳题做桥接检查。所有把 U 升成 S 的路径只走一个准入点，升级后重新过出处门。
5. **整句护栏（代码）**：某一句的结构层报了警，但这一句的整句判定是有证据的 S，就撤回这个报警。父节点复核默认关闭。
6. **输出（代码）**：在树上汇总判定，按偏移从原文切出引文，写判定理由，最后过响应约束。

## 不信任模型输出：确定性校验

所有方法的响应最后都过同一套响应约束（[`output/contract.py`](../src/verifier/output/contract.py)）：
- 每个引文的段号必须在范围内。
- 每段引文必须是 `context_passages[index]` 的逐字子串。偏移由代码重新推出来；引文在别的位置出现过，就重新锚定到那里。
- 判 S 或 C 却没有一条引文留下来的 claim，降成 U，并记下降级的原因。
- U 的引文列表必须为空。

OST 的引文本来就是按偏移从原文切的，响应约束对它只是最后一道检查。对 minimal_llm 来说，它是模型写的引文和响应之间唯一的防线。

## 错误边界和边界情况

| 情况 | 处理 |
|---|---|
| 请求体不合法 | 422 |
| 输入超过入口上限 | 413 |
| 原文为空 | 每条 claim 都判 U，不发判定请求 |
| 回答为空或只有空白 | 200，返回空的 claim 列表 |
| 没有可核对事实的回答（比如「无法根据给定段落回答」） | 输出一条 U |
| 模型输出格式坏 | llm 拆分器修一次还坏，就退回整句当单元；判定阶段坏了返回 502 |
| 上游 API 出错 | 可重试的错误重试 3 次，还失败返回 503；不可重试的返回 502 |

这些都有离线测试（[`tests/`](../tests/)），模型行为用假对象按脚本给出，不需要 API key。

## 它不做的

- 这条路径上没有确定性的数字或否定检查。只有 baseline 有。
- 先按句判定的 S 取的是 Jev 的最高选项，不设概率门槛。逐条判定时，低于 0.55 但倾向 S 的仍判 S。所以「拿不准就判 U」不是绝对的。
- 组装出来的 claim 不是回答的逐字片段。
- 原文树只在原文超过约 2.6 万 token 时才建，长原文的成本会上一个台阶，见[成本](cost.zh-CN.md)。
