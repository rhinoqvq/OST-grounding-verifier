# 评测集与指标

[返回 README](../README.zh-CN.md)

## 数据集准备以及处理

附带的评测集是 [`benchmark/ost30.jsonl`](../benchmark/ost30.jsonl)，30 题。每一行就是一个 `/verify` 请求，金标照作业的响应格式写。冻结后的哈希在 [`benchmark/ost30.sha256`](../benchmark/ost30.sha256)，跑分脚本发现文件和哈希对不上就拒跑。

这套题是我们根据开发中发现的 OST 的特性专门设计的。每题对应一个题型，考的是一个具体的机制，比如数字差一、否定反转、相似实体的属性错绑、超长原文、原文里藏着提示注入。题目都是从外部的公开数据集里找的，回答和标注尽量用数据集原来的。所以结果要读成「这个机制在对应的题型上成不成立」，不读成命中率。题是我们挑的、围着我们的架构设计的，这一点放在最前面说清楚。

### 题库

- **主题库是 ANAH**（Apache-2.0）。它是生成式问答：每个话题给参考文档、问题，以及两个模型的回答，一个看着文档作答，一个不看。回答逐句标了「无幻觉 / 矛盾 / 无法核实 / 非事实」，有幻觉的句子还附了订正。我们只用英文部分。
- **只用维基百科文档。** ANAH 的参考文档里有一部分是 Encyclopaedia Britannica 的词条，有版权，不能放进公开仓库。这些文档一律去掉。去掉以后，回答里所有 S 和 C 句的引文都还落在剩下的文档里，这条回答才用。U 句不用重新核对，因为拿掉一篇文档只会让证据变少。
- **ANAH 覆盖不了的题型**，从其他公开集补：RAGTruth、FOLIO、MuSiQue、FaithEval、VitaminC、SciTab。
- **公开集里也找不到的四个题型**（10、20、25、28），在 ANAH 的维基百科文档里按规则找一段符合结构的真实原文，再按固定的改法写出回答，金标在写的时候就定了。
- **不用的数据**：开发集 RAGTruth（2,700 条，开发时一直在用）、已经当外部基准跑过全量的 LLM-AggreFact，以及开发中看过的任何题。

### 抽取流程

1. 每个题型按规则筛出候选池。规则只用数据集自己的标签、订正和表面特征（关键词、长度、句数、词面重合）。
2. 候选池用固定种子 `20261022-<题型编号>` 打乱，得到固定的顺序。
3. 按顺序往下取，取到的第一条符合题型的就是这一题。跳过的情况有：话题已被别的题型用过、引文修不成原文的逐字子串、去掉 Britannica 后不再满足题型、人工核对后不符合题型。每一条跳过都写了理由。
4. 复核时发现题不符合或标签有错，就加进跳过清单、写明理由，换成下一条。每次替换都留了记录，不为了让某个方法得分而换题。

每个题型的筛选规则、种子和跳过理由，见[附录：OST30 抽取标准](appendix/ost30-extraction.zh-CN.md)。

ANAH 的引文是参考片段，不一定是原文的逐字子串。我们按「原样匹配 → 去掉句末句号 → 放宽空白 → 按省略号或句界拆开」依次修，每一块都要在原文里找到、而且不短于 15 个字符，修不好的回答不用。

### 金标和复核

- **金标从哪来**：ANAH 的题用 ANAH 人工核过的句子级标签；其他公开集的题用各数据集自己的标签；合成回答的题，金标在写回答时就定了。
- **粒度是句子**：回答里每个事实句算一条 claim，全集 71 条（S 34、U 26、C 11）。ANAH 的人工标注本来就是句子级的，拆成原子事实，等于用我们自己的标注替换掉人工标注。各方法拆出的 claim 打分时要对回到它所在的句子上，见下面的「打分规则」。
- **判定口径按作业的定义**：S 是被原文完全蕴含，C 是被原文直接反驳，其余都是 U。原标签和这个口径不一致时按口径改，每处改动都在那一题的 `notes.label_changes` 里写明原标签、改成什么、理由。另外三条：
  - 事实句一律算 claim，只有客套话、拒答这类不含可核对事实的句子才不算；
  - 引文要撑住整条 claim 里的每个事实；
  - 「因此」「此外」这类连接词不单独算断言，只有句子的主要断言就是因果时才按因果核对。
- **冻结**：30 题全部人工复核完以后冻结。冻结前没有任何方法跑过这些题。第一次跑分后改了三处（04 和 15 各一条 S 改成 U，20 题的注入改成定向给错误判定，免得照做的方法白拿分），改完重新冻结、换了哈希，所有方法整套重跑。之后金标不再改。
- **已知、保留的瑕疵**：15 题第 4 条判 S 是对的，但 ANAH 给的引文撑不住这句，评分引文时单独排除。13 题的别名对应偏浅，21 题 ANAH 是整句判的，测不到「只错一部分」。

许可证和逐题出处见 [`benchmark/DATA_LICENSE.md`](../benchmark/DATA_LICENSE.md)。数据集按 CC BY-SA 4.0 发布，因为原文里有维基百科、FOLIO、VitaminC 的文本。

## 打分规则

脚本是 [`benchmark/score_ost30.py`](../benchmark/score_ost30.py)。各方法只收到 `context_passages` 和 `generated_answer`，claim 由各方法自己拆，从不取金标的 claim。

1. **对齐**：系统的每条 claim 先按原文字符串在回答里定位（去掉句末标点再试一次）。盖住两句以上金标句各一半以上的，算一次「合并」，判定同时记给这几句；否则归到重叠最多的那句。在回答里找不到原文的（被系统改写过的 claim），按实词重合率归到最像的金标句，两个方向取大，到 0.5 才算对上。规则都放不下的，人工放，记在 [`benchmark/ost30_align_adjudication.json`](../benchmark/ost30_align_adjudication.json)。
2. **一句被拆成几条**：取最重的判定，C > U > S。
3. **漏判**：没有任何系统 claim 对上的金标句记为漏判，准确率算错，报警算漏报。
4. **整题全对**：每句判定都对，并且多出来的 claim 和非事实句上没有误报。
5. **引文命中**：金标 S / C 而且判对的句子，系统引文和金标引文在同一段原文里有重叠就算命中。
6. **引文撑不撑得住**：只比标签会放过「判对了但理由不对」的情况，所以另报一个准确率：S / C 判对，还要引文真能撑住这条 claim 才算对。对不上金标引文的，逐条人工判断，记在 [`benchmark/ost30_cite_adjudication.json`](../benchmark/ost30_cite_adjudication.json)。

## 指标

| 指标 | 看什么 |
|---|---|
| claim 准确率 | 71 条金标 claim 里判对的比例 |
| 三分类 macro-F1 | S、C、U 各自的 F1 取平均，C 只有 11 条，这一项对 C 的错更敏感 |
| C/U 报警 F1 | 把 C 和 U 都当「报警」，看报警抓得准不准、全不全 |
| 回答级 F1 | 一题当一个单位：这段回答有没有错。作业里「检出幻觉」最直接的指标 |
| 字符级 F1 | 系统判 C / U 的 claim 在回答里的字符区间，对金标错误片段算 F1。看「错在哪」标得准不准 |
| 真错判成 S | 37 条有错的 claim 里，被判成支持的条数。这是最危险的错 |
| 整题全对 | 30 题里每句都判对的题数 |
| 耗时 | 每题从发请求到拿到响应的时间，p50 / p95 |
| 成本 | 调用台账的 token 数乘标价，见[成本](cost.zh-CN.md) |

**区间**：每个方法自己的区间按题重采样 2,000 次。方法之间的差用配对重采样，10,000 次，种子 20261022。29 和 30 两题共用原文，重采样时算作一组。30 题给出的区间很宽，所以方法之间分不出高下的，我们不说谁胜谁负。

## 开发集和测试集

- **OST30 是随作业提交的测试集。** 冻结以后金标不再改。
- **RAGTruth 全量 2,700 条是开发集。** 迭代和消融都在它上面做，绝对分数偏乐观，用来比机制之间的差。它的 900 条 QA 回答（QA-900）是每个版本的回归测试。RAGTruth 只标了幻觉片段，没拆 claim、没给证据，所以在它上面只看回答级 F1 和字符级 F1，按任务分层做配对 bootstrap。RAGTruth 的打分脚本和运行记录没有放进仓库，这些数字是开发过程的记录。
